# Dataset Engineering Decision Analysis & Research Architecture

**Project:** *Adaptive Temporal-Relational Intrusion Detection for Evolving Network Traffic: Investigating Classical, Quantum, and Continual Learning Approaches*

---

## 1. Executive Decision Summary & Architectural Philosophy

Rather than building a single concatenated dataset, this project employs a **provenance-aware, multi-tiered data architecture**. This approach avoids combining datasets with shared underlying traffic while establishing a unified canonical schema capable of supporting:
1. **Classical & Deep ML Baselines** (tabular flow features)
2. **Temporal Sequence Models** (chronologically ordered event windows & IAT dynamics)
3. **Dynamic Graph Neural Networks** (time-evolving relational graphs $G_t = (V_t, E_t)$)
4. **Temporal–Relational Fusion Networks**
5. **Zero-Day Generalization** (strict attack-family holdout)
6. **Continual Learning & Concept Drift Streams** (chronological non-stationary domain shifts)

```
                            DATASET ECOSYSTEM
                                   │
         ┌─────────────────────────┼─────────────────────────┐
         │                         │                         │
    CIC ECOSYSTEM           UNSW ECOSYSTEM            IoT / SDN ECOSYSTEM
  (Enterprise Emulation)    (Synthetic / Mixed)      (Specialized Environments)
         │                         │                         │
    ┌────┴────────────┐            ├── UNSW-NB15             ├── ToN_IoT (NF-ToN-IoT-v2/v3)
    │                 │            │   (CSV / PCAP)          ├── CICIoT2023 (IoT Topology)
CIC-IDS2017     CSE-CIC-IDS2018    └── NF-UNSW-NB15-v2/v3    └── InSDN (SDN Environment)
```

## 3. Multi-Dimensional Compatibility Scoring Matrix

Each candidate dataset is evaluated across 8 weighted criteria (Total = 100%):

$$\text{Score} = 0.20 T + 0.20 R + 0.15 F + 0.10 A + 0.10 Q + 0.10 L + 0.10 P + 0.05 C$$

* **$T$ (Temporal, 20%):** True timestamp availability, sub-second precision, inter-arrival time (IAT), flow duration.
* **$R$ (Relational, 20%):** Unmasked Source/Destination IP, Source/Destination Port, Protocol, L4/L7 endpoints.
* **$F$ (Feature Compatibility, 15%):** Bidirectional packet/byte counts, flow metrics, rate indicators.
* **$A$ (Attack Diversity, 10%):** Attack classes, multi-stage attack scenarios, contemporary attack profiles.
* **$Q$ (Data Quality, 10%):** Absence of corrupted records, infinite/NaN artifacts, duplicated rows, extraction bugs.
* **$L$ (Label Quality, 10%):** Flow-level ground truth accuracy, verifiable timing alignment.
* **$P$ (Provenance & Independence, 10%):** Verifiable capture pipeline, availability of raw PCAPs.
* **$C$ (Continual Learning Suitability, 5%):** Natural chronological drift, distinct multi-day progression.

## 5. The CIC-IDS2017 $\leftrightarrow$ LYCOS-IDS2017 Data-Quality Sensitivity Paradigm

`CIC-IDS2017` and `LYCOS-IDS2017` share identical raw packet captures, but `LYCOS-IDS2017` addresses several known issues:
* **TCP Flow Termination:** Fixes FIN/RST teardown handling that caused fragmented and mismatched bidirectional flow summaries in `CICFlowMeter`.
* **Calculation Flaws:** Corrects negative IAT values, zero-duration division errors, and NaN values.
* **Feature Redundancies:** Eliminates collinear duplicate features (e.g., `Fwd Header Length` vs. `Fwd Header Length.1`).
* **Ground Truth Realignment:** Aligns flow timestamps with attack execution schedules.

### Experimental Design for Extractor Sensitivity
```
  [Train on CICFlowMeter Features] ──► [Test on LycoSTand Features]  (Tests vulnerability to extraction bugs)
  [Train on LycoSTand Features]    ──► [Test on CICFlowMeter Features] (Tests robustness to feature drift)
```
This isolates the impact of extraction artifacts on intrusion detection performance while keeping the underlying traffic distribution constant.

## 6. The Standardized NetFlow Architecture & Common Flow Representation

The University of Queensland NetFlow initiative (`NF-UNSW-NB15-v2/v3`, `NF-CSE-CIC-IDS2018-v2/v3`, `NF-ToN-IoT-v2/v3`, `NF-BoT-IoT-v2/v3`) provides a standard base schema across heterogeneous captures:
* Identical NetFlow v9/IPFIX 43-feature canonical format.
* Consistent units: Duration in milliseconds, rates in bytes/pkts per sec, timestamps in Unix Epoch.
* Preserved endpoint identities (`IPV4_SRC_ADDR`, `IPV4_DST_ADDR`, `L4_SRC_PORT`, `L4_DST_PORT`, `PROTOCOL`).

```
                    HETEROGENEOUS NETWORK CAPTURES
               (UNSW-NB15, CSE-CIC-IDS2018, ToN-IoT, etc.)
                                  │
                                  ▼
                     CANONICAL 6-GROUP FLOW SCHEMA
                                  │
          ┌───────────────────────┴───────────────────────┐
          ▼                                               ▼
  TEMPORAL WINDOWING ENGINE                      DYNAMIC GRAPH ENGINE
 (Chronological Slotted Windows)              (Temporal Snapshots $G_t$)
          │                                               │
  [Sequence: $F_{t-k} \dots F_t$]               [Nodes: IPs | Edges: Flows]
  • Inter-arrival time dynamics                  • Topological centrality
  • Burst metrics & rate shifts                  • Neighbor communication patterns
          │                                               │
          └───────────────────────┬───────────────────────┘
                                  ▼
                    TEMPORAL-RELATIONAL FUSION
             (Classical ML, GNN-LSTM/Transformer, Quantum)
```

## 8. Derived Temporal Features & Dynamic Windowing Engine

Raw network flow records are sorted in strict chronological order ($t_0 \le t_1 \le t_2 \le \dots \le t_N$).

```
             TIME-SLICED CHRONOLOGICAL WINDOW ($W_{\Delta t}$)
    ├─────────────────────────────────────────────────────────────────┤
    │ Flow 1: [Host A ──► Host B] (t = 0.01s, 443, 1420 bytes)        │
    │ Flow 2: [Host A ──► Host C] (t = 0.04s,  80,  512 bytes)        │
    │ Flow 3: [Host D ──► Host A] (t = 0.09s,  22,   64 bytes)        │
    │ Flow 4: [Host A ──► Host E] (t = 0.12s, 445, 1024 bytes)        │
    └─────────────────────────────────────────────────────────────────┘
```

### Derived Features per Window ($\Delta t = 10\text{s}, 30\text{s}, 60\text{s}$ or $K = 32, 64, 128$ events)

1. **Entity-Level Flow Deltas:**
   $$\Delta t_{\text{prev\_src}}(i) = t_i - \max \{ t_j \mid j < i, \text{src}(j) = \text{src}(i) \}$$
   $$\Delta t_{\text{prev\_dst}}(i) = t_i - \max \{ t_j \mid j < i, \text{dst}(j) = \text{dst}(i) \}$$

2. **Pairwise Inter-Flow Velocity:**
   $$\Delta t_{\text{pair}}(i) = t_i - \max \{ t_j \mid j < i, \text{src}(j) = \text{src}(i) \land \text{dst}(j) = \text{dst}(i) \}$$

3. **Window Burst Rates:**
   $$\text{FlowRate}_{W}(u) = \frac{|\{f \in W \mid \text{src}(f) = u\}|}{|W|}$$
   $$\text{ByteBurst}_{W}(u) = \sum_{f \in W, \text{src}(f) = u} \text{bytes}(f)$$

## 9. Relational Graph Construction: Evolving Temporal Snapshots

For each discrete temporal window $W_k = [t_k, t_k + \tau]$, we construct a directed multi-graph snapshot:

$$G_k = (V_k, E_k, X_{v,k}, X_{e,k})$$

```
                   DYNAMIC GRAPH SNAPSHOT: G_k
                          (Window: [t_k, t_k + \tau])

         [Host A] ──────────────── (443, TLS, 8.2KB) ───────────────► [Host B]
            │                                                            ▲
            │                                                            │
    (80, HTTP, 1.2KB)                                            (22, SSH, 450B)
            │                                                            │
            ▼                                                            │
         [Host C] ──────────────── (445, SMB, 3.4KB) ───────────────► [Host D]
```

* **Nodes ($V_k$):** Unique IP addresses active in $W_k$.
* **Node Feature Vector ($X_{v,k}$):**
  * In-degree: $d_{\text{in}}(v) = |\{ (u, v) \in E_k \}|$
  * Out-degree: $d_{\text{out}}(v) = |\{ (v, w) \in E_k \}|$
  * Unique Destination Ratio: $\frac{|\{w \mid (v, w) \in E_k\}|}{d_{\text{out}}(v)}$
  * Destination Port Diversity (Entropy): $H_p(v) = -\sum_{p} P(p) \log_2 P(p)$
  * Transmitted/Received Volume Ratio: $\frac{\sum \text{bytes}_{\text{out}}(v)}{\sum \text{bytes}_{\text{in}}(v) + \epsilon}$
* **Directed Edges ($E_k$):** Communication flows from $\text{src\_ip} \to \text{dst\_ip}$.
* **Edge Feature Vector ($X_{e,k}$):** Standardized bidirectional flow features (bytes, packets, rates, duration, flags).

### Key Takeaway
We have established a clear dataset selection and engineering structure. The datasets are organized by provenance, mapped to a unified canonical schema with temporal and relational extensions, and prepared for rigorous cross-dataset and continual-learning evaluation.




This sharpens your research focus into a **scientifically rigorous, controlled comparative experiment**.

When evaluating multimodal or multi-branch architectures (such as **Temporal + Relational Fusion**), varying both the encoders and the fusion mechanism simultaneously introduces confounding variables. 

By **holding the dataset representation, the temporal encoder, and the behavioral/relational encoder constant**, any variation in detection accuracy, convergence rate, zero-day resilience, or computational efficiency is **strictly attributable to the fusion strategy itself**.

## 2. Dataset Selection: What Datasets Justify This Evaluation?

To fairly benchmark fusion strategies without dataset artifacts, the dataset must satisfy three strict requirements:
1. **Rich Temporal Structure:** Continuous microsecond/millisecond timestamps with natural burstiness and inter-arrival time (IAT) dynamics.
2. **Rich Relational Structure:** Sufficiently dense multi-host communication (unmasked IP/ports) so that the graph branch has genuine topological signal (centrality, degree distribution, community structure).
3. **Attack Heterogeneity:** Attacks that express themselves *temporally* (e.g., slow DoS, brute force), *relationally* (e.g., distributed DDoS, port scans), and *both* (e.g., multi-stage botnets/infiltration).

### Recommended Primary Dataset Selection

| Dataset | Why It Justifies the Fusion Experiment |
| :--- | :--- |
| **Primary: `NF-CSE-CIC-IDS2018-v3`** *(or `CSE-CIC-IDS2018`)* | **Best overall candidate.** Contains a large enterprise topology (hundreds of victim servers and attacking hosts), spans multiple days with clear chronological progression, and includes attacks where neither temporal nor relational alone is sufficient (e.g., Botnet, Infiltration, Multi-source DDoS). |
| **Validation / Secondary: `NF-UNSW-NB15-v3`** | Cyber-range environment with 9 diverse attack families. Used to confirm that the best fusion strategy is not overfitted to the CIC network topology. |

> [!IMPORTANT]
> **Why NSL-KDD is disqualified:** NSL-KDD lacks real IP addresses and continuous time. You cannot construct dynamic topological graphs ($G_t$) from it, rendering the relational branch trivial and invalidating fusion comparison.

## 3. The Fixed Components Specification

To isolate the fusion module, the two input branches remain frozen in architecture across all fusion experiments:

### A. Fixed Temporal Component ($\mathcal{E}_{\text{temp}}$)
* **Input:** Chronological sequence of $K$ consecutive flows within window $W_t$:  
  $$S_t = [f_{t-K+1}, f_{t-K+2}, \dots, f_t] \in \mathbb{R}^{K \times d_f}$$
* **Encoder:** Fixed GRU / LSTM or 1D-CNN temporal feature extractor.
* **Output:** Temporal embedding vector $h_{\text{temp}} \in \mathbb{R}^{D}$.

### B. Fixed Behavioral / Relational Component ($\mathcal{E}_{\text{rel}}$)
* **Input:** Directed graph snapshot $G_t = (V_t, E_t)$ corresponding to the exact same temporal window $W_t$, where nodes $V_t$ are active IP hosts and edges $E_t$ are active flows.
* **Encoder:** Fixed 2-layer Graph Attention Network (GAT) or GraphSAGE.
* **Output:** Graph/relational summary embedding $h_{\text{rel}} \in \mathbb{R}^{D}$ (via global graph pooling over active nodes).

## 4. The Fusion Strategies to Benchmark

With $h_{\text{temp}}$ and $h_{\text{rel}}$ fixed to dimension $D$, you evaluate different fusion paradigms:

```
┌───────────────────────────┬─────────────────────────────────────────────────────────────┐
│ Fusion Strategy           │ Mathematical Formulation & Mechanism                        │
├───────────────────────────┼─────────────────────────────────────────────────────────────┤
│ 1. Early / Concatenation  │ $z = \text{MLP}([h_{\text{temp}} \,\|\, h_{\text{rel}}])$   │
│    (Standard Baseline)    │ Simple linear/non-linear projection of joint representation │
├───────────────────────────┼─────────────────────────────────────────────────────────────┤
│ 2. Gated / Adaptive       │ $g = \sigma(W_g [h_{\text{temp}} \,\|\, h_{\text{rel}}])$   │
│    Multimodal Fusion      │ $z = g \odot h_{\text{temp}} + (1 - g) \odot h_{\text{rel}}$│
│                           │ Dynamically weights temporal vs. relational importance     │
├───────────────────────────┼─────────────────────────────────────────────────────────────┤
│ 3. Bilinear / Tensor      │ $z = h_{\text{temp}}^T \mathcal{W} h_{\text{rel}} + b$      │
│    Product Fusion         │ Captures full second-order cross-modal feature interactions │
├───────────────────────────┼─────────────────────────────────────────────────────────────┤
│ 4. Cross-Attention        │ $Q = W_Q h_{\text{temp}}, \; K = W_K h_{\text{rel}}, \; V = W_V h_{\text{rel}}$ │
│    Co-Attention Fusion    │ Temporal features query relational topology & vice versa    │
├───────────────────────────┼─────────────────────────────────────────────────────────────┤
│ 5. Late / Decision-Level  │ $\hat{y} = \alpha \cdot \text{Softmax}(C_{\text{temp}}(h_{\text{temp}})) + (1-\alpha) \cdot \text{Softmax}(C_{\text{rel}}(h_{\text{rel}}))$ │
│    Ensemble Fusion        │ Independent branch predictions combined at probability tier │
├───────────────────────────┼─────────────────────────────────────────────────────────────┤
│ 6. Quantum / Variational  │ $| \psi(h_{\text{temp}}, h_{\text{rel}}) \rangle = U_{\text{PQC}}(\theta) | \phi(h) \rangle$ │
│    Quantum Circuit Fusion │ Quantum state entanglement of temporal & relational states  │
└───────────────────────────┴─────────────────────────────────────────────────────────────┘
```

## 5. Dataset Engineering Requirements to Support This Design

To make this benchmark work without data flaws, our dataset engineering pipeline must provide **synchronized dual-representation generation**:

```
                       RAW FLOW DATASET (Chronologically Ordered)
                                          │
                        SLICED INTO FIXED TIME WINDOWS (W_t)
                                          │
               ┌──────────────────────────┴──────────────────────────┐
               ▼                                                     ▼
     WINDOW FLOW SEQUENCE (S_t)                           GRAPH SNAPSHOT (G_t)
     • Array of shape (K, d_features)                     • PyTorch Geometric Data object:
     • Retains inter-flow time deltas                       - x: Node features (degree, host profile)
     • Sorted: t_1 <= t_2 <= ... <= t_K                     - edge_index: [src_ips, dst_ips]
                                                            - edge_attr: flow statistical features
               │                                                     │
               └──────────────────────────┬──────────────────────────┘
                                          ▼
                      SYNCHRONIZED BENCHMARK SAMPLE: (S_t, G_t, Y_t)
```

### Key Engineering Guarantees We Must Implement:
1. **Temporal-Relational Synchronization:** For every window index $t$, the flow sequence $S_t$ and graph $G_t$ contain the exact same underlying network events.
2. **Deterministic Windowing:** Standardize window size (e.g., fixed $\Delta t = 30\text{s}$ or fixed $K = 64$ flows) across all experiments.
3. **Consistent Ground Truth ($Y_t$):** Window is assigned an attack label if any flow within $W_t$ is malicious, with the dominant attack family recorded.
4. **Leakage-Free Splits:** Chronological split (e.g., first 70% time for train, next 15% validation, final 15% test) so temporal dependencies are respected.
